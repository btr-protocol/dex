# ERC1155 Design Choices

## Overview

BTR uses ERC1155 (Multi-Token Standard) for LP tokens with custom rebasing mechanics. This document explains all design decisions, trade-offs, and implementation details.

**Core Design Principles:**
1. **Single contract per pool**: All LP tokens for assets in a pool share one ERC1155 contract
2. **Asset-based token IDs**: Token ID = asset address (cast to uint256)
3. **Rebasing via scaled balances**: Aave-style accounting for auto-compounding fees
4. **Standard compliance**: Full ERC1155 compatibility for wallet/DEX integration
5. **Pool-aware metadata**: URIs include both pool and asset addresses

---

## Why ERC1155 Over ERC20?

### Alternative Considered: Individual ERC20 Per Asset

**ERC20 Approach:**
```
Pool has N assets → Deploy N separate ERC20 contracts
WETH LP: ERC20 contract at 0xAAA...
USDC LP: ERC20 contract at 0xBBB...
WBTC LP: ERC20 contract at 0xCCC...
```

**ERC1155 Approach:**
```
Pool has N assets → Deploy 1 ERC1155 contract
WETH LP: Token ID = uint256(0x7ceB...f619)
USDC LP: Token ID = uint256(0x2791...4174)
WBTC LP: Token ID = uint256(0x2260...92BA)
```

### Comparison

| Aspect | ERC20 (N contracts) | ERC1155 (1 contract) | Winner |
|--------|---------------------|----------------------|--------|
| **Deployment Gas** | ~1.5M × N | ~2.5M (one-time) | ERC1155 for N>2 |
| **Storage Overhead** | N × (name, symbol, decimals) | Single contract storage | ERC1155 |
| **Transfer Gas** | ~50k per token | ~50k per token | Tie |
| **Batch Transfers** | N separate txs | Single tx for N tokens | ERC1155 |
| **Wallet Support** | Universal | Modern wallets | ERC20 (slightly) |
| **DEX Integration** | Native support | Requires mapping | ERC20 |
| **Metadata** | Static (immutable) | Dynamic URI | ERC1155 |
| **Code Complexity** | Factory pattern needed | Single implementation | ERC1155 |
| **Upgrade Path** | N separate upgrades | Single upgrade | ERC1155 |

### Key Trade-offs

**✅ ERC1155 Advantages:**
1. **Gas Efficiency at Scale**: For pools with 5+ assets, deployment savings > 5M gas
2. **Atomic Multi-Asset Operations**: Deposit/withdraw multiple assets in one tx
3. **Unified Liquidity**: All LP tokens share the same contract address
4. **Simplified Factory**: No need for LP token factory deployment logic
5. **Dynamic Metadata**: Can update token metadata without redeploying

**⚠️ ERC1155 Disadvantages:**
1. **Wallet UX**: Some wallets show ERC1155 tokens in "Collectibles" instead of "Tokens"
2. **DEX Support**: Requires token ID mapping layer (not native address-based)
3. **Market Cap Tracking**: Aggregators need custom integration
4. **Slightly Higher Single-Asset Cost**: First-time ERC1155 interaction costs ~2.5M gas vs ~1.5M for ERC20

### Decision: ERC1155

**Rationale:**
- BTR pools typically have 3-10 assets → Net gas savings significant
- Modern wallet support for ERC1155 is excellent (MetaMask, Rabby, Rainbow)
- Dynamic metadata enables rich LP token information
- Batch operations unlock better UX for multi-asset LPs
- Single contract simplifies auditing and upgrades

## Token ID Scheme

### Design: Direct Address Casting

```solidity
function addressToTokenId(address token) internal pure returns (uint256 id) {
    assembly { id := token }
}

// Reverse conversion
address token = address(uint160(id));
```

### Properties

**Bijection:**
- Every asset address maps to exactly one token ID
- Every token ID maps to exactly one asset address
- No collisions possible (address space = 160 bits < 256 bits)

**Gas Efficiency:**
- Zero-cost conversion (pure assembly cast)
- No storage lookups required
- No token ID registry to maintain

**Predictability:**
- Token ID deterministically derived from asset address
- No need to query contract to find token ID
- Off-chain tools can calculate token IDs independently

### Alternative Considered: Sequential Token IDs

```solidity
// Alternative: Sequential IDs
mapping(address => uint256) public assetToTokenId;
mapping(uint256 => address) public tokenIdToAsset;
uint256 public nextTokenId = 1;

function addAsset(address token) external {
    assetToTokenId[token] = nextTokenId;
    tokenIdToAsset[nextTokenId] = token;
    nextTokenId++;
}
```

**Why Rejected:**
- Requires 2 storage slots per asset (40k gas overhead per asset)
- Adds query complexity (need to call contract to find token ID)
- Increases contract size and complexity
- No meaningful benefits over direct casting

→ Token ID: 701332046859776641134542099953513155635840574233

**Verifiable Off-Chain:**

## Rebasing Mechanism

### Design: Scaled Balances + Liquidity Index

**Problem:**
Standard ERC1155 stores absolute balances. Fee compounding would require:
- Minting new tokens to all holders (gas: O(N) where N = number of holders)
- Or manual claiming (poor UX, requires regular user action)

**Solution:**
Store **scaled balances** and apply a growing **liquidity index** on reads.

### Data Structures

```solidity
struct LPState {
    uint128 totalScaledSupply;   // Sum of all scaled balances
    uint128 liquidityIndex;       // Rebasing multiplier (starts at 1e18)
}

mapping(address => mapping(address => uint256)) scaledBalances;
// scaledBalances[user][asset] = user's scaled balance
```

### Balance Calculation

```solidity
function balanceOf(address owner, uint256 id) public view returns (uint256) {
    address token = address(uint160(id));
    LPState storage lpState = _s().lpStates[token];

    if (lpState.liquidityIndex == 0) return 0;

    uint256 scaledBalance = _s().scaledBalances[owner][token];
    return (scaledBalance * lpState.liquidityIndex) / PRECISION;
}
```

**Key Property:**
- `scaledBalance` never changes (except on deposit/withdraw/transfer)
- `liquidityIndex` grows as fees accrue
- Result: `balanceOf()` automatically increases over time

### Fee Accrual

When swap fees accrue to an asset:

```solidity
function accrueFeesToLPs(
    Asset storage asset,
    LPState storage lpState,
    uint256 feeAmount
) internal {
    if (lpState.totalScaledSupply == 0) return;
    if (feeAmount == 0) return;

    // Add fee to reserves
    uint256 oldReserves = asset.reserves;
    asset.reserves = oldReserves + feeAmount;

    // Update liquidity index: newIndex = oldIndex × newReserves / oldReserves
    if (oldReserves > 0) {
        uint256 newIndex = (uint256(lpState.liquidityIndex) * asset.reserves) / oldReserves;
        lpState.liquidityIndex = uint128(newIndex);
    }
}
```

**Gas Cost:** O(1) - only updates 2 storage slots regardless of number of LPs

### Numerical Example

```
Initial State:
├─ reserves: 1000 USDC
├─ totalScaledSupply: 1000
├─ liquidityIndex: 1.0e18
└─ Alice scaled balance: 100

Alice LP balance: (100 × 1.0e18) / 1e18 = 100 LP tokens

Swap generates 50 USDC fee:
├─ newReserves: 1050 USDC
├─ newIndex: (1.0e18 × 1050) / 1000 = 1.05e18
├─ totalScaledSupply: 1000 (unchanged)
└─ Alice scaled balance: 100 (unchanged)

Alice LP balance: (100 × 1.05e18) / 1e18 = 105 LP tokens (+5%)

Effect: All LPs automatically earned 5% more tokens
```

### Deposit Mechanics

```solidity
function deposit(address token, uint256 amount, uint256 minLpTokens)
    external returns (uint256 lpTokens)
{
    LPState storage lpState = _s().lpStates[token];
    Asset storage asset = _s().assets[token];

    // Calculate LP tokens to mint
    if (lpState.totalScaledSupply == 0) {
        lpTokens = amount;  // First deposit: 1:1 ratio
    } else {
        lpTokens = (amount × totalScaledSupply × PRECISION) /
                   (reserves × liquidityIndex);
    }

    // Calculate scaled amount to store
    uint256 scaledAmount = (lpTokens × PRECISION) / liquidityIndex;

    // Update state
    lpState.totalScaledSupply += scaledAmount;
    asset.reserves += amount;
    _s().scaledBalances[msg.sender][token] += scaledAmount;

    // Mint ERC1155 token
    _mint(msg.sender, addressToTokenId(token), lpTokens, "");
}
```

**Key Properties:**
1. LP tokens minted proportional to deposit amount and current liquidity
2. Scaled balance stored (not absolute balance)
3. Future fee accruals automatically increase this user's balance

### Withdraw Mechanics

```solidity
function withdraw(address token, uint256 lpTokens, uint256 minAmountOut)
    external returns (uint256 amountOut)
{
    LPState storage lpState = _s().lpStates[token];
    Asset storage asset = _s().assets[token];

    // Convert LP tokens to scaled amount
    uint256 scaledAmount = (lpTokens × PRECISION) / liquidityIndex;

    // Calculate underlying token amount
    amountOut = (scaledAmount × liquidityIndex × reserves) /
                (totalScaledSupply × PRECISION);

    // Apply withdrawal fee (if any)
    uint256 withdrawalFee = calculateWithdrawalFee(asset);
    if (withdrawalFee > 0) {
        uint256 feeAmount = (amountOut × withdrawalFee) / BPS_PRECISION;
        amountOut -= feeAmount;
        accrueFeesToLPs(asset, lpState, feeAmount);  // Remaining LPs benefit
    }

    // Update state
    lpState.totalScaledSupply -= scaledAmount;
    asset.reserves -= amountOut;
    _s().scaledBalances[msg.sender][token] -= scaledAmount;

    // Burn ERC1155 token
    _burn(msg.sender, addressToTokenId(token), lpTokens);
}
```

**Key Properties:**
1. User receives their proportional share of reserves
2. Scaled balance removed from state
3. Withdrawal fees accrue to remaining LPs (discourages mercenary capital)

### Alternative Considered: Share Price Approach (ERC4626-style)

```solidity
// Alternative: Track total shares and compute price per share
uint256 totalShares;
uint256 totalAssets;

function balanceOf(address owner, uint256 id) returns (uint256) {
    uint256 shares = _balances[owner][id];
    return (shares × totalAssets) / totalShares;
}
```

**Why Rejected:**
- Requires division on every balance check (more gas)
- Share price can decrease (negative APY possible)
- More complex to reason about for users
- Aave-style index is industry-proven pattern

## Transfer Mechanics

### ERC1155 Standard Compliance

BTR fully implements ERC1155 with custom transfer hooks:

```solidity
function safeTransferFrom(
    address from,
    address to,
    uint256 id,
    uint256 amount,
    bytes calldata data
) public override {
    // Standard ERC1155 checks
    if (msg.sender != from && !isApprovedForAll(from, msg.sender)) {
        revert Unauthorized();
    }

    // Update balances (overridden from Solady ERC1155)
    uint256 fromBalance = balanceOf(from, id);
    if (fromBalance < amount) revert InsufficientBalance();

    // Call hook to update scaled balances
    _afterTokenTransfer(from, to, [id], [amount]);

    // Standard receiver check
    if (to.code.length != 0) {
        if (IERC1155Receiver(to).onERC1155Received(msg.sender, from, id, amount, data)
            != IERC1155Receiver.onERC1155Received.selector) {
            revert TransferRejected();
        }
    }
}
```

### Scaled Balance Update Hook

```solidity
function _afterTokenTransfer(
    address from,
    address to,
    uint256[] memory ids,
    uint256[] memory amounts
) internal {
    BAMMStorage storage $ = _s();

    for (uint256 i; i < ids.length; ++i) {
        address token = address(uint160(ids[i]));
        LPState storage lpState = $.lpStates[token];

        // Safety check: token must be initialized
        if (lpState.liquidityIndex == 0) {
            if (amounts[i] > 0) revert NotInitialized();
            continue;
        }

        // Convert amount to scaled amount
        uint256 scaledAmount = (amounts[i] × PRECISION) / lpState.liquidityIndex;

        // Update scaled balances
        if (from != address(0)) {
            uint256 fromBalance = $.scaledBalances[from][token];
            if (fromBalance < scaledAmount) revert InsufficientBalance();
            $.scaledBalances[from][token] = fromBalance - scaledAmount;
        }
        if (to != address(0)) {
            $.scaledBalances[to][token] += scaledAmount;
        }
    }
}
```

**Key Properties:**
1. Transfers update scaled balances (not absolute balances)
2. Scaled amount calculated using current liquidityIndex
3. Both sender and receiver maintain proportional fee earnings
4. Batch transfers supported (standard ERC1155 feature)

### Transfer Example

```
Initial:
├─ Alice scaled balance: 100
├─ Bob scaled balance: 50
├─ liquidityIndex: 1.2e18
├─ Alice LP tokens: (100 × 1.2e18) / 1e18 = 120
└─ Bob LP tokens: (50 × 1.2e18) / 1e18 = 60

Alice transfers 30 LP tokens to Bob:
├─ scaledAmount: (30 × 1e18) / 1.2e18 = 25
├─ Alice new scaled: 100 - 25 = 75
├─ Bob new scaled: 50 + 25 = 75
├─ Alice LP balance: (75 × 1.2e18) / 1e18 = 90
└─ Bob LP balance: (75 × 1.2e18) / 1e18 = 90

Future fee accrual (10% increase):
├─ newIndex: 1.32e18
├─ Alice LP balance: (75 × 1.32e18) / 1e18 = 99
└─ Bob LP balance: (75 × 1.32e18) / 1e18 = 99

Both continue earning proportional fees after transfer
```

## URI and Metadata

### URI Format

```solidity
function uri(uint256 id) public view override returns (string memory) {
    address token = address(uint160(id));
    return string(abi.encodePacked(
        "https://btr.supply/pool/",
        toHexString(address(this)),  // Pool address
        "/",
        toHexString(token)            // Asset address
    ));
}
```

### Design Decision: Pool + Asset in URI

**Problem:**
Multiple BTR pools can exist (e.g., USDC-based, USDT-based, DAI-based). Each pool can contain WETH LP tokens.

**Without Pool Address:**
```
Pool A WETH LP: https://btr.supply/pool/7ceb23fd6bc0add59e62ac25578270cff1b9f619
Pool B WETH LP: https://btr.supply/pool/7ceb23fd6bc0add59e62ac25578270cff1b9f619
→ Both have same URI! Metadata collision!
```

**With Pool Address:**
```
Pool A WETH LP: https://btr.supply/pool/<pool-a>/7ceb23fd6bc0add59e62ac25578270cff1b9f619
Pool B WETH LP: https://btr.supply/pool/<pool-b>/7ceb23fd6bc0add59e62ac25578270cff1b9f619
→ Unique URIs, distinct metadata ✓
```

**Key Benefits:**
1. **Unique Identification**: Each pool+asset combo has distinct URI
2. **Metadata Routing**: Server can return pool-specific metadata
3. **APY Differentiation**: Different pools may have different APYs for same asset
4. **Reserve Tracking**: Each pool has independent reserve amounts

### Metadata Response Schema

```json
{
  "name": "BTR WETH LP",
  "description": "Liquidity Provider token for WETH in BTR Pool",
  "symbol": "BTR-WETH-LP",
  "decimals": 18,
  "image": "https://btr.supply/assets/weth-lp.png",
  "properties": {
    "pool": "0x1234567890abcdef1234567890abcdef12345678",
    "asset": "0x7ceB23fD6bC0adD59E62ac25578270cFf1b9f619",
    "assetSymbol": "WETH",
    "reserves": "125.3",
    "liquidityIndex": "1.0523",
    "totalSupply": "118.9",
    "apy": "12.5%",
    "volume24h": "$2.5M",
    "fees24h": "$8.6K"
  },
  "localization": {
    "uri": "https://btr.supply/pool/{locale}/<pool>/<asset>",
    "default": "en",
    "locales": ["en", "es", "zh", "ja"]
  }
}
```

### Static vs Dynamic Metadata

**BTR Choice: Dynamic**

```solidity
function uri(uint256 id) public view override returns (string memory)
// Returns URL, not embedded JSON
```

**Rationale:**
- Reserves, APY, volume change continuously
- Embedding JSON in contract → stale data
- Dynamic server can query blockchain for latest values
- Standard wallet/marketplace support for URL-based metadata

### Alternative Considered: On-Chain Metadata

```solidity
// Alternative: Return JSON directly
function uri(uint256 id) public view returns (string memory) {
    return string(abi.encodePacked(
        "data:application/json;base64,",
        Base64.encode(bytes(abi.encodePacked(
            '{"name":"BTR WETH LP","image":"...",',
            '"properties":{"reserves":"', reserves.toString(), '"}}'
        )))
    ));
}
```

**Why Rejected:**
- Gas cost to update metadata: O(N × log(reserves))
- Cannot include off-chain data (APY, volume, prices)
- Inflexible (requires contract upgrade to change schema)
- Poor UX (stale data in wallets until page refresh)

## Batch Operations

### Batch Transfer

```solidity
function safeBatchTransferFrom(
    address from,
    address to,
    uint256[] calldata ids,
    uint256[] calldata amounts,
    bytes calldata data
) public override;
```

**Use Case:**
Send LP tokens for multiple assets in a single transaction.

**Example:**
```solidity
// Transfer WETH LP, USDC LP, WBTC LP in one tx
uint256[] memory ids = [
    uint256(uint160(WETH)),
    uint256(uint160(USDC)),
    uint256(uint160(WBTC))
];
uint256[] memory amounts = [10e18, 100e6, 0.5e8];

bamm.safeBatchTransferFrom(alice, bob, ids, amounts, "");
```

**Gas Savings:**
- Single transfer: ~50k gas
- Batch 3 transfers: ~70k gas (~40% savings vs 3 separate txs)

### Batch Balance Query

```solidity
function balanceOfBatch(
    address[] calldata owners,
    uint256[] calldata ids
) public view override returns (uint256[] memory);
```

**Use Case:**
Query LP balances for multiple users/assets in one call.

**Example:**
```solidity
// Get Alice and Bob's WETH + USDC LP balances
address[] memory owners = [alice, alice, bob, bob];
uint256[] memory ids = [
    uint256(uint160(WETH)),
    uint256(uint160(USDC)),
    uint256(uint160(WETH)),
    uint256(uint160(USDC))
];

uint256[] memory balances = bamm.balanceOfBatch(owners, ids);
// [aliceWETH, aliceUSDC, bobWETH, bobUSDC]
```

## Security Considerations

### 1. Reentrancy Protection

All state-changing functions use OpenZeppelin's `nonReentrant` modifier:

```solidity
function deposit(...) external nonReentrant { ... }
function withdraw(...) external nonReentrant { ... }
function swap(...) external nonReentrant { ... }
```

**Rationale:**
- External token transfers (ERC20) can callback into contract
- Rebasing mechanism relies on consistent state
- Batch operations increase attack surface

### 2. Integer Overflow Protection

Solidity 0.8+ built-in overflow checks + explicit casts:

```solidity
lpState.totalScaledSupply = Cast.toUint128(lpState.totalScaledSupply + scaledAmount);
// Cast.toUint128() reverts on overflow
```

### 3. Division by Zero Protection

```solidity
if (lpState.liquidityIndex == 0) {
    lpState.liquidityIndex = PRECISION;  // Initialize to 1.0
}
```

### 4. First Depositor Attack Prevention

```solidity
if (asset.reserves == 0 && amount < asset.minLiquidity) {
    revert BelowMinimumLiquidity();
}
```

**Attack Vector:**
1. Attacker deposits 1 wei
2. Directly transfers 1000 tokens to contract
3. Next depositor gets unfavorable exchange rate

**Mitigation:**
- Require minimum first deposit (e.g., 1e6 for USDC)
- Locks initial liquidity in contract
- Makes manipulation prohibitively expensive

### 5. Scaled Balance Underflow Protection

```solidity
if (fromBalance < scaledAmount) revert InsufficientBalance();
scaledBalances[from][token] = fromBalance - scaledAmount;
```

**Prevents:**
- Transferring more than owned
- Negative balances
- Balance inflation attacks

## Gas Analysis

### Per-Operation Gas Costs

| Operation | ERC20 | ERC1155 (BTR) | Difference |
|-----------|-------|---------------|------------|
| **First mint** | ~50k | ~50k | ~0% |
| **Subsequent mint** | ~30k | ~30k | ~0% |
| **Transfer** | ~50k | ~52k | +4% |
| **Batch transfer (3)** | ~150k | ~70k | -53% |
| **Balance query** | 2.5k | 3k | +20% |
| **Batch balance (3)** | 7.5k | 4k | -47% |
| **Approval** | ~45k | ~45k | ~0% |

**Takeaways:**
- Single operations: Nearly identical gas costs
- Batch operations: Significant savings (30-50%)
- Balance queries: Slightly higher (extra index calculation)

### Fee Accrual Gas Cost

```solidity
function accrueFeesToLPs(...) internal {
    asset.reserves += feeAmount;           // SSTORE: 20k gas
    lpState.liquidityIndex = newIndex;     // SSTORE: 20k gas
}
```

**Total: ~40k gas per fee event**

**vs. ERC20 Fee Distribution:**
```solidity
// Would need to mint tokens to N holders
for (uint256 i; i < holders.length; ++i) {
    _mint(holders[i], feeShare);  // N × 20k gas
}
```

**ERC1155 Savings:**
- N=10 holders: ~160k gas saved
- N=100 holders: ~1.96M gas saved
- N=1000 holders: ~19.96M gas saved

**Conclusion:** Rebasing mechanism is O(1) vs O(N) for explicit distribution

## Testing Recommendations

### Core Invariants

1. **Scaled Supply Consistency**
   ```solidity
   assert(sum(scaledBalances[user][token]) == lpState.totalScaledSupply);
   ```

2. **Balance Consistency**
   ```solidity
   assert(balanceOf(user, tokenId) == (scaledBalances[user][token] * liquidityIndex) / PRECISION);
   ```

3. **Index Monotonicity**
   ```solidity
   assert(liquidityIndex[t+1] >= liquidityIndex[t]);
   ```

4. **Total Value Conservation**
   ```solidity
   assert(totalLPValue ≈ asset.reserves);
   ```

### Edge Cases

- [ ] First deposit with minimum liquidity
- [ ] Deposit/withdraw when index = 1.0
- [ ] Transfer with zero amount
- [ ] Transfer before asset initialized
- [ ] Batch transfer with mixed initialized/uninitialized assets
- [ ] Fee accrual with totalScaledSupply = 0
- [ ] Integer overflow on large deposits
- [ ] Rounding errors with very small balances
- [ ] Reentrancy via malicious ERC1155Receiver

### Fuzz Testing

```solidity
function testFuzz_DepositWithdrawInvariant(uint256 amount) public {
    amount = bound(amount, MIN_LIQUIDITY, type(uint96).max);

    uint256 lpTokens = bamm.deposit(WETH, amount, 0);
    uint256 balanceBefore = asset.reserves;

    bamm.withdraw(WETH, lpTokens, 0);

    uint256 balanceAfter = asset.reserves;
    assertApproxEqRel(balanceBefore, balanceAfter, 0.01e18); // 1% slippage
}
```

## Conclusion

BTR's ERC1155 implementation achieves:

✅ **Gas Efficiency**: O(1) fee accrual vs O(N) for ERC20 minting
✅ **Scalability**: Single contract for N assets
✅ **User Experience**: Auto-compounding fees, no manual claims
✅ **Standard Compliance**: Full ERC1155 compatibility
✅ **Flexibility**: Dynamic metadata, batch operations
✅ **Security**: Proven rebasing pattern (Aave-inspired)

**Trade-offs Accepted:**
- Slightly higher balance query gas (~500 gas)
- Requires modern wallet support
- Custom DEX integration layer needed

**Overall Assessment:**
ERC1155 with scaled balances is the optimal choice for multi-asset LP tokens with rebasing mechanics. The gas savings at scale and UX improvements outweigh the minor wallet compatibility concerns.
